# روش تست E2E (تست رو مرورگر واقعی) — راهنمای قابل استفاده برای هر پروژه

## تفاوت اصلی: چند نوع تست وجود داره؟

تو این پروژه چهار نوع چک مختلف داریم، و هرکدوم چیز کاملاً متفاوتی رو تضمین می‌کنن:

| نوع چک | چی رو تضمین می‌کنه | چی رو **تضمین نمی‌کنه** |
|---|---|---|
| `tsc --noEmit` (TypeScript) | کد از نظر «نوع داده» (type) درسته — مثلاً یه عدد جای متن پاس نداده باشی | هیچی درباره‌ی رفتار واقعی صفحه |
| `eslint` | سبک کد و الگوهای مشکل‌دار شناخته‌شده | هیچی درباره‌ی رفتار واقعی صفحه |
| `npm run build` | کد کامپایل می‌شه، صفحات prerender می‌شن بدون کرش | هیچی درباره‌ی این‌که تو مرورگر واقعی درست *نمایش* داده می‌شه یا نه |
| **تست E2E (Playwright)** | یه مرورگر واقعی (Chrome/Safari) صفحه رو باز می‌کنه، دقیقاً مثل یه کاربر واقعی کلیک می‌کنه، فرم پر می‌کنه، و چک می‌کنه چیزی که *واقعاً رو صفحه ظاهر می‌شه* درسته یا نه | — |

**نکته‌ی مهم:** سه تای اول همه‌شون رو کد اجرا می‌شن، نه رو یه صفحه‌ی واقعی. یعنی می‌تونن ۱۰۰٪ تمیز رد بشن درحالی‌که خود سایت رو مرورگر واقعی یه چیز اشتباه نشون بده. **دقیقاً همین امروز اتفاق افتاد**: باگ عنوان صفحه (title) هیچ‌وقت با `tsc`/`eslint`/`build` پیدا نمی‌شد — چون از نظر کد هیچ خطایی نداشت، فقط Next.js تو مرورگر واقعی رفتار متفاوتی نشون می‌داد. فقط تست E2E این رو گرفت.

## تست E2E دقیقاً چطور کار می‌کنه؟

1. **یه مرورگر واقعی (نه شبیه‌سازی) باز می‌شه** — Playwright واقعاً Chromium/WebKit رو نصب و اجرا می‌کنه، دقیقاً همون موتوری که تو مرورگر کاربر واقعی هست.
2. **به آدرس واقعی سایت زنده می‌ره** (`https://www.certcoach.de`، نه یه نسخه‌ی لوکال یا شبیه‌سازی‌شده).
3. **کارهایی که یه کاربر واقعی می‌کنه رو انجام می‌ده**: کلیک، تایپ تو فرم، اسکرول، صبر کردن برای بارگذاری.
4. **چک می‌کنه چیزی که واقعاً رو صفحه هست با انتظارمون یکیه** — نه چیزی که تو کد نوشته شده، بلکه چیزی که مرورگر واقعاً رندر کرده.
5. اگه فرق داشت، **عکس صفحه (screenshot)** هم می‌گیره، دقیقاً لحظه‌ی خطا.

## چرا این با «تست دستی خودم» فرق داره؟

- **خودکاره** — هر بار که کد عوض بشه، خودش دوباره اجرا می‌شه (هر ۶ ساعت، یا با یه دکمه)، نیازی نیست خودت هر دفعه دستی کلیک کنی.
- **حافظه نداره ولی هیچ‌وقت خسته نمی‌شه** — یه انسان بعد از چندبار تست، جاهای تکراری رو رد می‌کنه؛ این هربار همه‌چیز رو کامل چک می‌کنه.
- **شواهد واقعی می‌ده، نه حدس** — به‌جای این‌که بگم «فکر کنم درسته»، دقیقاً می‌گه کدوم صفحه، کدوم عنصر، و چرا.

## محدودیت مهمی که امروز باهاش روبه‌رو شدیم

من (Claude) تو یه محیط جدا (sandbox) کار می‌کنم که دسترسی اینترنتش محدوده — نمی‌تونم مستقیم مرورگر Playwright رو اجرا کنم چون سرور دانلودش تو لیست مجاز نیست. **راه‌حلی که پیدا کردیم:**
1. تست‌ها رو می‌نویسم و از نظر کد (tsc/eslint) تأیید می‌کنم
2. یه فایل «GitHub Actions workflow» می‌سازم که رو سرورهای گیت‌هاب (نه sandbox من) اجرا می‌شه
3. با یه توکن گیت‌هاب، از طریق API خود گیت‌هاب `trigger`ش می‌کنم
4. نتیجه‌ی خلاصه (موفق/شکست) رو از API می‌گیرم
5. **ولی متن دقیق خطا رو یه سرور دیگه (Azure Blob Storage) نگه می‌داره که به اون هم دسترسی ندارم** — پس تو باید متن کامل لاگ رو از صفحه‌ی Actions گیت‌هاب کپی و برام بفرستی، من تحلیلش می‌کنم و درستش می‌کنم.

## چطور برای پروژه‌ی بعدی همینو راه بندازم؟

اگه یه پروژه‌ی Next.js دیگه داری (یا حتی یه فریمورک دیگه، Playwright از همه پشتیبانی می‌کنه)، این قدم‌ها رو تکرار کن:

### ۱. نصب
```bash
npm install -D @playwright/test
```

### ۲. فایل تنظیمات (`playwright.config.ts`)
```typescript
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  use: {
    baseURL: process.env.BASE_URL || "https://YOUR-SITE.com",
    screenshot: "only-on-failure",
  },
  projects: [
    { name: "chromium", use: { ...devices["Desktop Chrome"] } },
  ],
});
```

### ۳. یه تست ساده بنویس (`e2e/homepage.spec.ts`)
```typescript
import { test, expect } from "@playwright/test";

test("homepage loads and has the right title", async ({ page }) => {
  await page.goto("/");
  await expect(page).toHaveTitle(/YourBrandName/i);
});
```

### ۴. یه GitHub Actions workflow بساز (`.github/workflows/e2e.yml`)
```yaml
name: E2E Health Check
on:
  workflow_dispatch: {}
  schedule:
    - cron: "0 */6 * * *"
jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
        env:
          BASE_URL: https://YOUR-SITE.com
```

### ۵. برای اجرای دستی (بدون نیاز به من)
```bash
npx playwright install --with-deps   # فقط یه‌بار
npx playwright test                  # اجرای تست‌ها
npx playwright test --ui             # حالت تصویری، خیلی مفید برای دیباگ
```

### نکته‌ی طلایی که امروز یاد گرفتیم
وقتی چند تا element مشابه تو صفحه هست (مثلاً یه فرم تماس اصلی + یه فرم خبرنامه تو فوتر که هر دو `<form>` و `input type="email"` دارن)، locator رو باید **scope** کنی — یعنی به یه بخش خاص محدودش کنی، نه کل صفحه:

```typescript
// ❌ اشتباه — به همه‌ی فرم‌های صفحه برمی‌خوره
page.locator('form input[type="email"]')

// ✅ درست — فقط به فرم تو بخش اصلی صفحه محدود می‌شه
page.getByRole("main").locator('form input[type="email"]')
```

---

**خلاصه‌ی یه‌خطی برای یادت بمونه:** تست E2E یعنی یه ربات که دقیقاً مثل یه کاربر واقعی، با یه مرورگر واقعی، سایت زنده رو کلیک می‌کنه و چک می‌کنه — و تنها چیزیه که می‌تونه باگ‌هایی رو پیدا کنه که کد از نظر تایپ‌اسکریپت/لینت/بیلد کاملاً تمیزه ولی تو مرورگر واقعی رفتار عجیب داره (دقیقاً مثل باگ عنوان صفحه‌ی امروز).
